# ModelForge 开发路线与架构决策记录

> 这份文档同时承担两个职责：给协作者看的路线图，以及**架构决策记录**（ADR）。
> 每个决策都写下「为什么」——因为「做了什么」代码里有，「为什么这么做」只有这里才有。

## 架构决策记录

### ADR-001：人在环中（HITL），不做全自动

**决策**：Agent 在每个关键节点（拆题、选模、定参数）抛出候选方案 + 理由，由用户拍板后继续。

**理由**：全自动方案（输入赛题 → 输出论文）实现上就是一条长 prompt 串代码执行，
看起来震撼，但绕开了 Agent 工程真正困难的部分。「中断-决策-恢复」才是最有价值的技术点。

### ADR-002：HITL 用「状态落盘 + 点击时重建」

**决策**：每个节点跑完即把状态存入 SQLite；用户决策后从 checkpoint 重建上下文继续。

**理由**：进程内挂起（await 一个 Future）实现简单，但服务重启就丢进度、无法水平扩展。
落盘式的代价是复杂度，换来的可恢复性和可部署性值得。

**推论（重要）**：checkpoint 的 schema 必须在 M1-M2 就定下来，不能拖到 M4 ——
整个编排层是围绕它生长的。

### ADR-003：Provider 抽象层，内部统一用 OpenAI 格式

**决策**：定义归一化的流式事件模型；内部消息格式直接采用 OpenAI 的 chat 格式。

**理由**：实测 DeepSeek / 通义 / Kimi / Ollama / vLLM 全部兼容 OpenAI 协议，
用它当内部标准意味着只有一个 Provider 需要写真正的转换代码（Anthropic）。

**已知代价**：OpenAI 的概念会渗透到上层状态机。这是被接受的取舍，不是疏忽。

### ADR-004：Provider 层不做重试

**决策**：一旦流开始吐字节，出错就产出 `ErrorEvent` 并结束，绝不自动重试。
连接建立**之前**的失败由 SDK 的 `max_retries` 处理。

**理由**：流一旦开始就无法回滚。重试会让用户看到前半句被重复输出。
而且只有上层状态机知道当前跑到哪一步、用户等了多久，重试决策权归它。

**实现**：`ErrorEvent.retryable` 字段把这个判断的结论一并交给上层。

### ADR-005：沙箱必须使用独立运行时环境

**决策**：执行 LLM 生成代码的沙箱**不得**与后端共用 `.venv`。
因此 `pyproject.toml` 里刻意没有 numpy / scipy / matplotlib。

**理由**：同一个环境里跑不可信代码，等于把整个项目和 API Key 都交出去
（`os.environ["DEEPSEEK_API_KEY"]` 一行就能读走）。这不是洁癖，是安全边界。

**推论**：沙箱环境在 M3 单独创建。

### ADR-006：图表与 UI 共用一套色彩体系

**决策**：`web/src/app/globals.css` 是全站视觉的唯一真相来源。组件内禁止硬编码色值。

**理由**：ModelForge 是图表密集型产品。UI 一套色、图表另一套色，成品会像两个产品拼起来的。

**硬性约束（由配色校验计算得出，非审美偏好）**：
- 亮色模式下有 3 个分类色对比度低于 3:1 → 图表必须带**直接标签或表格视图**
- 暗色模式最差相邻 CVD ΔE = 10.3（危险区）→ **必须启用次级编码**（标签/间隙/纹理）

**合起来**：图表永远不能只靠颜色区分系列。

### ADR-007：Agent 自称「蒟蒻」

**决策**：Agent 在文案中自称「蒟蒻」（网络语，新手、菜鸟）。

**理由**：与 ADR-001 自洽 —— 一个承认自己拿不准、每个决策点都停下来问用户的 Agent，
自称越谦逊，交互越不违和。这个调性延续到 Agent 提示词和各处界面文案。

**落地**：`modelforge/agents/prompts.py` 的 `SYSTEM_PROMPT`。前端不传 system 消息时
由后端兜底注入 —— 人设是服务端资产，换人设不该要求用户清浏览器缓存。

### ADR-008：SSE 客户端用 `fetch` + `ReadableStream`，不用 `EventSource`

**决策**：前端手写 SSE 帧解析（`web/src/lib/sse.ts`），不用浏览器内置的 `EventSource`。

**理由**（三条，前两条是硬约束，第三条是它反而帮了我们）：

1. **`EventSource` 只支持 GET，不能带请求体。** 而我们要把整个对话历史发过去，
   天然是 POST 语义。塞进 query string 既有长度上限（几轮对话就爆），
   又会让对话内容完整地留在服务器访问日志里。
2. **`EventSource` 不能发自定义请求头。** M6 要加鉴权时只能退而求其次用 Cookie
   或 query 参数，而后者会把 token 写进日志。
3. **自动重连在这里是有害的。** 普通 SSE（行情、通知）重连是好事，接着收就行；
   但生成流重连意味着**重新跑一遍模型** —— 用户会看到前半句被重吐一遍，
   还白花一份 token。

**修正一处先前的判断**：M2 计划里把「不能自动重连」列成了方案 A 的代价。
权衡时发现这条写反了 —— 对这个场景它恰恰是优点。**待定**状态的解除，
靠的不是收集更多信息，而是发现原先把某一项的符号搞错了。

**已知代价**：约 60 行手写解析（字节碎片 + 帧碎片两级缓冲），且断线不会自愈。
断线恢复交给 M4 的 checkpoint 机制：重连 = 从落盘状态开一条新流，
而不是让传输层偷偷重放。

### ADR-009：会话状态用**事件日志**，不是快照

**决策**：每一步 append 一条不可变记录；当前状态是**重放**出来的，不直接存。

**背景**：ADR-002 说了「状态落盘」，但没说什么形态。有两条路：

    ① 快照 —— 每个节点跑完，把完整状态覆盖写一行。恢复 = 读那一行。
    ② 事件日志 —— 每一步 append 一条不可变记录，状态靠重放推导。

**理由**：快照只能回答「现在是什么」，日志能回答「当时为什么」。

具体到这个产品，差别体现在一个高频动作上：**「换个模型再算一遍对比」**。
在快照模型下，这要么做不到，要么得把整个历史重建一遍；
在日志模型下，它天然成立（从某个决策点截断、重放）。

而且决策记录本身**就是产品价值** —— 「用户在第 3 步选了 AHP，
理由是数据不方便说」这种结构化的事实，混在聊天文本里是查不出来的。

**代价（写在明处）**：

- **日志只能 append。** 将来的「回退改主意」必须是
  「从某条 `decision_answer` 之前截断，**且连同其后所有事件一起丢**」。
  截一半会得到一段非法历史（有 tool_call 却没有结果）。
  M5 加这个功能时必须按这条来，不能就地改一行。
- 每次 append 都要重放全部事件来刷新 `title` / `status` 两个缓存，
  是 O(会话长度)。以这个产品的规模（几十到几百条）完全不值得优化。
  真要优化，正确做法是加一个增量版本 **+ 一条断言「它和全量重算一致」的测试**，
  而不是把全量版本删掉。
- `agent_max_tool_rounds` 从「一次会话的总预算」降级成了「单轮的保险丝」——
  恢复是「重新跑一次 `run_agent_turn`」，每次都会重新计数。

**实现**：`modelforge/sessions/`（`base.py` 类型与协议 / `project.py` 投影 /
`sqlite_store.py` 持久化）。

### ADR-010：HITL 中断 = 一个「结果来自人」的工具调用

**决策**：`ask_user` 是一个和 `run_python` **平级**的工具。
中断不是「挂起生成器」，而是「如实记录一个还没有结果的工具调用，然后结束这条流」。

**理由**：这样整条恢复链路**没有一行「恢复」代码**：

    用户答完 → 答案 append 成一条事件 → 从日志重新投影出消息历史
             → **重新调用一次 `run_agent_turn`**

进程重启过、机器换过，都无所谓。而 M3 建好的整条工具调用链
（声明 → 碎片累积 → 派发 → 回填）几乎原样复用，只多了一条
「结果还没到」的分支。

**三条由此推出的设计**：

1. **一轮里遇到 `ask_user`，先执行完所有别的调用再中断**，
   而不是「停下来把后面的标记成已取消」。后者会产生一条会被
   `format_for_model` 渲染成「【沙箱未能执行代码】这不是你的代码的问题」的
   记录 —— 一句彻头彻尾的假话，会把模型引向完全错误的方向。
   （模型并行发起的调用本来就互不依赖，先跑完在语义上也对。）

2. **投影必须是全函数。** `project_messages` 遍历每条 assistant 的
   `tool_calls`，按它自己的顺序逐个找结果，找不到就补一条「未执行」。
   这把「历史永远合法」做成了**一个纯函数的性质**，而不是「写入方的纪律」——
   规范会被人忘掉，函数不会。

3. **`decision_request` 不投影进对话历史，`decision_answer` 投影。**
   不对称是刻意的：模型看到的是自己发出的那次 `ask_user` 调用（含原始
   arguments），所以请求不需要再给一遍；而答案它不知道，必须给。

**明确接受的取舍**：

- **用户中途刷新 = 一次没有回答的提问。** 已落一条 `aborted` 事件，
  但 M4 不做「继续这条被中断的流」的 UI。而且一轮生成只在跑完时才落盘，
  所以**用户看到过的半截文字，刷新后会消失**。
- **模型把 `run_python` 排在 `ask_user` 前面时，用户要先等一次
  最长 10 秒的沙箱执行**才能看到决策卡片。这是事件顺序的必然代价。

### ADR-011：产物走「约定目录 + 扫描」，引用跟着事件日志走

**结论**：沙箱每次执行的产物落在工作目录下的 `artifacts/` 子目录里，
执行结束时被扫描、搬进一个**项目之外**的存储目录，元数据作为
`ToolResult.artifacts` 跟着 `tool` 事件进日志。

**为什么不是「让模型显式声明它产出了什么」**：
后者要求模型每次都记得声明，而**它一定会忘** —— 忘了不会报错，
只是图凭空消失。约定目录下**它是写文件**，而写文件是它本来就在做的事。
这和 ADR-012 那条「风格靠环境不靠模型自觉」是同一条原则。

**为什么引用挂在 `ToolResult` 上，而不是新增一种日志事件**：
产物就是**一次工具调用的结果**。给它单开一种 `LogArtifact` 事件的话，
立刻要回答「它和那条 `tool` 事件怎么配对」—— 答案是靠 `call_id`，
于是同一件事有了两个真相源，而它们可以不一致。
挂在 `ToolResult` 上则完全不引入这种可能。

实际收益很具体：**刷新页面时产物自动就回来了**，一次新查询都不用写。
因为 M4 早就定下「`tool` 事件原样存整个 `ToolResult`」。

**为什么产物目录必须在项目之外**：这是 M3 坑 ② 的原样复刻，而且更难发现 ——
沙箱的 `solution.py` 是**每次执行**都触发 `--reload`（必中），
而产物只在**画图时**才落盘（偶发）。竞态 + 低频 = 最难查的组合，
看起来像「模型偶尔抽风」。`config.artifacts_dir` 的默认值因此从
`artifacts/`（会被锚到项目根）改成了系统应用数据目录。

**为什么不用 `StaticFiles` 挂一个目录出去**：一行就能搞定，但那样会把
整个产物根目录暴露成可枚举的静态资源。文件名是 uuid（看起来猜不到），
但那是**靠不可预测性当安全措施**，而不是靠访问控制 —— 前者一旦泄漏就
完全失效，后者不会。走显式路由的话，M6 加鉴权只是在它上面加一层依赖。

**明确接受的代价**：

- **产物元数据不可变。** 日志只能 append（ADR-009），所以想做「删掉某一个
  产物」，正确做法是删文件 + 追加一条「已删除」记录，不能回去把那条 ref 改了。
  M5 不做这个功能。
- **取消时这一轮的产物会丢。** 用户点停止时，工作目录连同里面画到一半的图
  一起被删。这和 ADR-009 已经接受的「被中断的那一轮已流出的文字会消失」
  是同一件事，口径一致。技术上可以用 `asyncio.shield` 包一次收集，
  但用户主动点了停止就意味着他不想等 —— 不值得为它加一层。
- **单次执行最多 20 个产物 / 50 MB**，超出部分**明确告知**（写进 stderr，
  模型看得到），不静默截断。

### ADR-012：论文级插图的风格靠环境保证，数据与图同源

**结论**：沙箱的 `MPLCONFIGDIR` 指向一个持久目录，里面放着仓库里的
`matplotlibrc`。于是**沙箱里任何 matplotlib 代码都会自动套上科研风格**，
不需要模型调用任何东西，也不依赖提示词。

**为什么不是「提供一个漂亮的 API，指望模型调用」**：模型会忘。忘了不报错，
只会安静地出一张宋体豆腐块 + 白底无网格的图，而你会以为是 matplotlib 的锅。
**风格必须由环境保证。** 辅助模块（`modelforge_plot`）只负责让它「更好」，
不是「不坏」的前提。

**三条硬约束，都是算出来的不是拍的**：

1. **中文与负号** —— `font.sans-serif` 首选 Noto Sans SC（中文黑体，
   西文由同一字体的拉丁字形渲染，字重一致）；
   `axes.unicode_minus: False`，不设这一条负号会变成豆腐块（中文衬线字体
   普遍没有 U+2212）。
2. **投稿可用** —— `pdf.fonttype: 42`。matplotlib 默认用 Type 3 位图字体，
   而**很多期刊的投稿系统直接拒收含 Type 3 的 PDF**。代价是两行配置。
3. **灰度可辨** —— 设计系统的结论是「图表永远不能只靠颜色区分系列」
   （见 ADR-006 的校验结果），而数模国赛论文经常黑白打印。
   `mp.style_lines(ax)` 按系列序号再叠一层线型和标记形状。

**数据与图同源**：`mp.save(fig, name, chart={...})` 在存图的同时写一份
`<name>.chart.json`，里面是**模型算出来的真实数组**（直接接受 numpy 数组）
加上图型、轴标签、配色。工作台据此渲染交互版本 —— 同一个数组，两个视图。

轴标签是**从 figure 里读**的，不让模型再传一遍；颜色按序号自动取调色板。
原则是「能让两处对不上的机会越少越好」。

**配色三处一致的机械保证**：`globals.css` 的 `--chart-cat-*`（真相源）、
`matplotlibrc` 的 `axes.prop_cycle`、`modelforge_plot.COLORS` 三份拷贝
由 `tests/test_palette_contract.py` 逐字节比对。沙箱是另一个 Python 环境，
读不到前端的 CSS，所以只能是拷贝 —— **三份拷贝就是三个会漂移的地方**，
而这个漂移的症状极温和（颜色偏一点，图照出、没人报 bug）。

**明确接受的取舍**：

- **`chart` 参数写歪了不抛异常，只打警告。** 图是主产物，数据是附带的；
  为了一份附带的东西让模型那段脚本当场死掉、后面所有的图都不画，是错的取舍。
  但警告必须能照着改（报错原文照打）。
- **`.chart.json` 这一轮只原样展示**，渲染成 ECharts 是下一轮的事。
  契约定在这里是因为**写存图逻辑的时候顺手写掉最便宜**，事后补要动三处。

### ADR-013：工作台外壳是三栏，状态留在页面组件里

**结论**：`/chat` 从一个单栏对话页变成三栏工作台 ——
**会话清单 · 对话 · 产物**。状态（会话列表、选中了哪个产物、
两栏的折叠）全部归 `page.tsx` 所有，不引入 context，也不引入状态库。

**为什么不是 `app/chat/layout.tsx`**：试过这个方向，它有三处硬伤 ——
① layout 拿不到 `searchParams`，于是侧栏没法知道「当前是哪个会话」，
只能去用 `useSearchParams()`，而那会**给整个路由段套上一层 Suspense**
（见 `page.tsx` 里那段说明）；② 状态只能从 layout 往 page 流，
page 的「建了新会话」传不回 layout，侧栏就刷不了；③ 切会话走的是
`replaceState` 改 `?s=`，layout **不会重新渲染**，高亮会停在旧的那个。

**为什么不是 context**：值得传的只有两个字段（`sessionId` 和
`openArtifactId`），而 `sessionId` 已经在走 `MessageBubble` → `ToolView`
→ `ToolCallCard` → `ArtifactGallery` → `ArtifactFile` 这条链路了。
多一个 prop 是线性的代价；而 context 在这个项目里有**非线性的**代价 ——
React Compiler **没有开启**（`next.config.ts` 是空的），内联的
`onOpenArtifact={() => …}` 每次渲染都是新函数，于是每次 `text_delta`
都会重渲染所有消费者。也就是说这里引入 context 反而更慢。

**产物面板和工具卡片里的缩略图是什么关系**：**两个层次，不是两份副本**。
工具卡片里那份是**局部上下文**（「这段代码生成了这张图」），
右栏那份是**全局清单**（这个会话一路产出了什么）。
图多到十几张时，前者要靠翻聊天记录找回来，后者一眼就能看到。
所以两边都留着。

**附带的一条**：工具卡片里原本那个「展开看原始 JSON」的 `ChartDataView`
被换成了「在工作台里打开」按钮 —— 面板现在真的能渲染那份数据了，
原样打印几百行花括号就只剩噪声。

### ADR-014：交互图从 CSS 变量实时取色，不用 `.chart.json` 里烤的那份

**结论**：`.chart.json` 里每个系列都带一个 `color`，那是 `mp.save()`
按序号从 `COLORS` 取的（**亮色模式**那一套）。屏幕上的交互图**不直接用它**——
它从 `--chart-cat-*` 实时读，那份烤进去的只在读不到令牌时兜底。

**理由**：那两份是为了不同的介质选出来的，不能混用。

    静态 PNG  → 印刷品，目标是白纸。亮色那套是对的。
    交互图    → 屏幕，可能在暗色模式里。而暗色模式是**重新选步号**，
                不是把亮色反转（`--chart-cat-1` 亮 `#2a78d6` / 暗 `#3987e5`，
                `--chart-cat-2` 亮 `#1baf7a` / 暗 `#199e70` —— 值之间没有
                任何公式关系，只能重新查表）。

直接用烤进去的亮色值，等于把 ADR-006 那条「暗色是重新选步」的结论
在图表这一层推翻，而且**看起来还行**（浅蓝画在深灰上当然看得见），
只是和工作台的其余部分不再是同一套色。

**为什么不让 ECharts 自己读 CSS 变量**：canvas 上的 `var(--x)`
是一个没有意义的字符串，必须由 JS 取出来变成字面量。

**实现被三条 lint 规则逼成了一个特定的形状**（写在
`app/chat/use-chart-tokens.ts` 的注释里）：在 render 里读 DOM 撞
`purity`；用 `useEffect` + `setState` 撞 `set-state-in-effect`；
在 `getSnapshot` 里现读现缓存撞 `immutability`（必须返回同一个引用，
否则无限重渲染）和 `globals`（渲染期不许写全局）。
最后的形状是**模块求值时读一次 + 一个模块级的 matchMedia 监听**，
`getSnapshot` 只读不写。

**明确的取舍**：

- **取不到令牌时回退到 `series[].color`，不报错。** 那仍然是一份
  真实的设计系统颜色（只是亮色那一版的），代价是暗色模式下颜色偏暗一点。
  比「整张图画不出来」划算，也比编一个硬编码色值诚实 ——
  组件里禁止硬编码色值这条规矩没有例外。
- **超过 8 个系列时颜色照旧按 8 循环**，和静态图保持一致，
  但**必须说出来**（面板上给一句说明）。同时折线叠了一层
  「线型 × 标记」（和 `modelforge_plot.GRAYSCALE_STYLES` 同一张表），
  所以重复的颜色仍然分得开 —— 这是设计系统要求的**次级编码**。
- **不启用 ECharts 的 `aria.decal`（纹理）**。它看起来是现成的
  「次级编码」，但默认会给柱/饼铺满斜线，而纹理会喧宾夺主
  （「纹理是选配，不是装饰」）。用线型代替。

      恢复能力移交 M4 的 checkpoint

### 三条关键设计

**① 错误分两层，两边都要处理**

    流开始**之前**  → HTTP 状态码（前端读 `response.ok`）
    流开始**之后**  → 带内 error 事件，HTTP 仍是 200

因为响应头必须在第一个字节发出前定死。只处理一层，就会有某条失败路径变成白屏。

**② 碎片是分层的**

M1 处理过「JSON 参数碎片」，M2 又遇到两种更隐蔽的：

    · 字节碎片 —— 中文占 3 字节，分片边界可能把一个汉字劈成两半
                  → `TextDecoder` 用 `{ stream: true }` 模式
    · 帧碎片   —— 一次 read 可能是半帧，也可能是三帧半
                  → 解码成文本后先攒 buffer，再按空行切

共同规律：**不要假设一次到达的就是一个完整单位。**

**③ Finish 一定是最后一个事件**

这条契约跨了三层（Provider → SSE → 前端 for-await 循环），
每层都有责任维护它。`chat.py` 里那道 `except` 保险就是为此存在的 ——
没有它，生成器抛异常会导致前端停在转圈上永远不动。

### M2 顺带修掉的两处旧问题

- `page.tsx` 的 `idle` 状态被删除。它与 `loading` 对用户是同一件事，
  而在 effect 里同步 setState 反而多触发一次渲染。（React Compiler 的
  `set-state-in-effect` 规则抓到的 —— 它抓的是性能症状，暴露的是建模冗余。）
- `performance.now()` 移出组件作用域（`purity` 规则）。时钟读取天然不纯，
  而组件作用域内的一切都被要求可重入。

### ⚠️ 两个只有端到端才测得出来的 bug

这一节是 M3 最值得留下的东西。两个 bug 都有同一个特征：
**86 个单元测试全绿，一接到真实服务器上就炸。**

**① `NotImplementedError:`（消息是空的）**

    起因：Windows 上 asyncio 的 SelectorEventLoop **根本不支持子进程**。
    修法：不用 asyncio 的子进程 API，改用 `asyncio.to_thread` 包阻塞式
          `subprocess.Popen`。任何事件循环都能跑。
    教训：**不要把功能正确性押在「服务器碰巧选了哪个事件循环」上。**
         而且这个选择发生在我们代码被 import 之前，应用层管不着。

**② 随机的 `KeyboardInterrupt`（退出码 3221225786）**

    起因：沙箱每次执行都往**项目目录内**写一个 `solution.py`，
         而 uvicorn 的 `--reload` 正盯着项目目录 ——
         一看有新文件就热重载，重载的终止信号顺着控制台传到了
         正在跑代码的沙箱子进程上。竞态，所以时灵时不灵，
         而第一次 `import numpy` 最慢、窗口最宽，看起来像「第一次必挂」。
    修法：工作目录挪到系统临时目录，并在配置落进项目里时打警告。
    证据：uvicorn 日志里那句
          `WatchFiles detected changes in 'sandbox_tmp\run-xxx\solution.py'. Reloading...`

**共同教训**：单元测试的**环境**往往比真实环境宽松（pytest 用默认事件循环、
不起 reloader）。所以「测试通过」给的是信心，不是证据 ——
每个里程碑都要真的把服务跑起来、用真模型走一遍。

⚠️ **给 M5 的提醒**：生成图表要存「产物」时，**不要**存进项目里的
`artifacts/`，那会重新触发问题 ②。存系统目录 + 接口下载，
或者给 uvicorn 配 `--reload-exclude`。

### 三处「单元测试全绿但真实运行会炸」的地方

这一节和 M3 那节一样，是最值得留下的东西。

**① 收尾轮的 assistant 消息从来没被落盘**（M4 最严重的一个）

    起因：循环只在「这一轮要调工具」的分支里把 assistant 消息写进历史。
          M2/M3 无所谓 —— 前端每次把全量历史重发一遍，看不出来。
          但 M4 的历史是从事件日志**投影**出来的，于是：

              用户：帮我算 1 到 100 的和
              蒟蒻：5050                     ← 这句话从来没被存下来
              用户：那乘 2 呢？               → 模型看到「我调了个工具，然后用户又问了新问题」
              刷新页面 → 刚才那句回答凭空消失

          而「刷新不丢」正是 M4 唯一的验收标准，而且是**每一次对话的
          每一次收尾**都会中招，不是边缘情况。

    修法：**不在三个出口各补一次写入**（正常结束 / 中断 / 轮数用尽）——
          那样漏一个就又是同一个 bug。改成把「生成 + 落盘」提到所有分支
          判断**之前**无条件执行，于是「N 轮生成 → N 条 assistant 记录」
          成为一条可以离线断言的不变式，三个出口自动全覆盖。

**② SQLite 的 `ON DELETE CASCADE` 默认是空操作**

    起因：外键约束要靠 `PRAGMA foreign_keys = ON` 打开，而且是**每条连接**
          各自设置的（不是数据库级的持久设置）。忘了它，删会话只删掉
          sessions 那一行，events 全变成孤儿数据 —— **不报任何错**，
          只是数据库慢慢变脏。

    同类还有三个：`busy_timeout` 默认 0（一有并发写立刻 database is locked）、
    `check_same_thread` 让连接绑定线程（连接必须在 `to_thread` 的工作函数
    **内部**创建，在外面建好传进去会时灵时不灵）、`journal_mode` 默认 DELETE。
    四条都在 `_connect()` 里无条件执行一遍。

**③ 测试跑了 lifespan，于是写进了项目里的真实数据库**

    起因：`main.py` 的启动钩子会清空所有会话租约（防止热重载把租约留给
          下一个进程），而 `test_stream.py` 的 client 夹具会**真的跑一遍
          lifespan**。结果跑一次测试就在项目目录里创建/改动了
          `data/modelforge.db`。

    后果有两层：脏是小事，**`--reload` 正盯着项目目录**是大事 ——
    那正是 M3 踩过的坑 ②。修法是加一个 autouse 的 conftest 夹具
    把存储指到 `tmp_path`，并在文件里写清楚「默认安全比记得做对可靠」。

### 一个只有端到端才看得出来的测试替身 bug

`test_stream.py` 的 `_FakeProvider` 里有这么一行：

    self.seen_messages = messages      # ← 存的是引用

Agent 循环会把传进去的历史列表**就地扩展**。M4 之前循环只在工具轮扩展它，
所以这个替身一直「对」；M4 让**每一轮**都扩展它之后，一个普通回答的测试
突然发现消息多了一条。

值得记住的是它的**表象**：测试红了，看起来像是被测代码的错。
诊断的第一步永远是问「是我的断言错了，还是被测的东西真的变了」。

**它是对的。** 方法没定就先画图才是错的，而这正是 HITL 的设计意图。
冒出问题的是脚本：它把「没产物」直接当成了失败，而真实原因需要一个
更具体的分支去识别。修法是在找产物**之前**先看有没有 `decision_request`，
并明确告诉人「这不是 bug，去界面上拍板，或者换个没有分岔口的提示词」。

### 三处「单元测试全绿但真实运行会炸」的地方

**① `matplotlibrc` 里写错了 7 个配置项，matplotlib 一个都没报错。**

它只往 stderr 打几行警告就过去了，程序照跑 —— 而后果是配色**静默**退回
默认的 tab10、网格颜色还是老样子、`subplot.hspace` 压根没生效。三个具体错误：

    subplot.hspace          正确的键是 `figure.subplot.hspace`
    cycler('color', [...])  正确写法是 `cycler(color=[...])`（关键字参数）
    grid.color: #e1e0d9     **必须加引号**，否则 `#` 被当注释砍掉

第三条最值得记：matplotlib 用 `cbook._strip_comment()` 砍行内注释，而它
**只认双引号**。所以 `cycler(color=['#2a78d6', ...])` 里的 `#` 会被砍掉，
整个值被截成 `cycler(color=['`。换成双引号才安全。

发现它靠的不是看日志，是**把值读回来逐项断言**。所以有了
`tests/test_matplotlib_style.py`（在真沙箱里读回来）和
`tests/test_palette_contract.py`（三份拷贝比对）。
**判据不能是「没报错」，得是「读回来确认值对了」。**

**② `MPLCONFIGDIR` 指向每次执行都删的工作目录，于是每张图都白交 0.42 秒。**

M3 把它设成 `<工作目录>/.mplconfig`，而工作目录用完即删 —— 每次
`import matplotlib.pyplot` 都要重建一遍字体缓存。实测：

    冷启动（无缓存） 0.870 s      热启动（有缓存） 0.453 s
    ─────────────────────────────────────────────
    白交的部分       0.42 s  ← 每次执行

说清楚量级：**这不致命**。每次执行是独立进程，代价不累积，10 秒的
超时预算里它占 4%。它不是「会炸」，是「每张图白交半秒」。

之所以还是记一笔，是因为它**没有任何症状**：图照出、结果照对，只是慢一点点。
这种问题不会有人来报 bug，只会让人觉得「这软件有点钝」。

**③ 测试会删掉用户真实的图。**

`main.py` 的 lifespan 启动时调 `sweep_orphans()`，删掉「不属于任何现存会话」
的产物目录。而测试里的会话存储是空的 —— 于是一次 `pytest` 运行会把用户
**所有**真实的图当成孤儿删光。这条路径只在「测试真的跑了一遍 lifespan」时
走到，也就是 `TestClient(create_app())` 那几个端到端夹具。

这是 M4 那条「测试会跑 lifespan，而启动钩子会清租约」的**同款问题的
更严重版本**：当时最坏是写脏一个项目内的数据库文件，这次是删用户目录里的东西。

修法是给 `conftest.py` 加产物隔离夹具，但**光加夹具不够**：`main.py` /
`api/artifacts.py` / `api/sessions.py` 里如果写成 `from modelforge.artifacts
import get_store`（导入时绑定函数对象），`monkeypatch` 就换不掉它。
必须写成 `artifact_store_pkg.get_store()`（运行时查模块属性）——
三条注释都写在这件事上，因为它**一旦写错，测试依然全绿**。

### 三处「单元测试全绿但真实运行会炸」的地方

**① `json.dumps` 会写出一个浏览器**读不了**的 JSON。**

    .venv 里：json.dumps({'data': [1.0, float('nan')]})  →  {"data": [1.0, NaN]}
    浏览器里：JSON.parse(...)                            →  SyntaxError

Python 的 `json` 默认 `allow_nan=True`，会把 `NaN` / `Infinity`
**原样写出去** —— 而这两个字面量不是合法 JSON。触发条件一点都不罕见：
归一化里的 `0/0`、`np.log(0)`、Excel 空单元格读进来的 `np.nan`。

症状的形状很坏：PNG 好好的、`.chart.json` 也在磁盘上、Python 读回来也正常，
**只有浏览器读不了**。而前端的兜底文案是
「读不到这份数据（文件可能已经不在了）」——**一句彻头彻尾的假话**，
把人和文件系统引向完全错误的方向。

发现它靠的是**真的去跑了一遍那两个 encode/decode**，
而不是「Python 的 json 应该没问题吧」。

修法两处：`_number()` 里拒绝非有限值（报错文案点名 `np.nan` / `log(0)`），
再把写入挪进那个 `try` 并加 `allow_nan=False` 当第二道防线 ——
后者是必须的，否则新加的异常会越过「图是主产物」那条取舍，
把模型整段脚本弄死。

**② ECharts 6 有一整套「不注册就没有、而且不报错」的东西。**

按需构建里没有白送的东西，而 v6 尤其：

    GridComponent    不再被折线/柱状图自动带上 —— 不注册，直角坐标系画不出来
    AriaComponent    不注册，`aria: {enabled: true}` 是个**静默的空操作**
    LabelLayout      不注册，所有标签排版规则（含 `hideOverlap`）全部失效
    CanvasRenderer   按需构建里**一个渲染器都不带**

还有一条更隐蔽的：**v6 换了默认主题**（配色重做、图例默认挪到画布底部）。
我们每一处颜色都显式给，所以不受影响 —— 但**漏给一处**就会静默地用上
v6 的新默认色，而它看起来「差不多对」，只是和工作台不再是同一套色。
防这一手的是：把设计系统那套色同时设成 ECharts 的**全局调色板**，
于是漏掉的地方至少落在我们的颜色上。

**③ 「切会话」引入的三处竞态，全都不报错。**

到 M4 为止这个页面自己建、自己用一个会话，所以从没遇到过这些问题。
M5b 让会话变成可以来回切的东西之后：

    ① 快速点 A、B → 两个 getSession 同时在飞，A 的响应后到会**覆盖 B 的界面**
       （表现：「我点的明明是 B」）
    ② 切走时正在跑的流不掐掉 → 后续事件写进**已经换掉的那个会话**的状态
    ③ 流的 `catch` / `finally` 也会 setState → 在切走之后给新会话
       安一个「生成中断了」的错误，而那个会话上什么都没发生

三处都用一个**单调递增的请求令牌**挡住（`loadSeqRef` / `streamSeqRef`）。
用递增整数而不是布尔：连切三次时需要知道「现在最新的是哪一次」。
