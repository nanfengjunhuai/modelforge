## 架构决策记录

### ADR-001：人在环中（HITL），不做全自动

**决策**：Agent 在每个关键节点（拆题、选模、定参数）抛出候选方案 + 理由，由用户拍板后继续。

**理由**：全自动方案（输入赛题 → 输出论文）实现上就是一条长 prompt 串代码执行，
看起来震撼，但绕开了 Agent 工程真正困难的部分。「中断-决策-恢复」才是最有价值的技术点。

### ADR-002：HITL 用「状态落盘 + 点击时重建」

**决策**：每个节点跑完即把状态存入 SQLite；用户决策后从 checkpoint 重建上下文继续。

**理由**：进程内挂起（await 一个 Future）实现简单，但服务重启就丢进度、无法水平扩展。
落盘式的代价是复杂度，换来的可恢复性和可部署性值得。

**推论（重要）**：checkpoint 的 schema 必须在 M1-M2 就定下来，不能拖到 M4 ——
整个编排层是围绕它生长的。

### ADR-003：Provider 抽象层，内部统一用 OpenAI 格式

**决策**：定义归一化的流式事件模型；内部消息格式直接采用 OpenAI 的 chat 格式。

**理由**：实测 DeepSeek / 通义 / Kimi / Ollama / vLLM 全部兼容 OpenAI 协议，
用它当内部标准意味着只有一个 Provider 需要写真正的转换代码（Anthropic）。

**已知代价**：OpenAI 的概念会渗透到上层状态机。这是被接受的取舍，不是疏忽。

### ADR-004：Provider 层不做重试

**决策**：一旦流开始吐字节，出错就产出 `ErrorEvent` 并结束，绝不自动重试。
连接建立**之前**的失败由 SDK 的 `max_retries` 处理。

**理由**：流一旦开始就无法回滚。重试会让用户看到前半句被重复输出。
而且只有上层状态机知道当前跑到哪一步、用户等了多久，重试决策权归它。

**实现**：`ErrorEvent.retryable` 字段把这个判断的结论一并交给上层。

### ADR-005：沙箱必须使用独立运行时环境

**决策**：执行 LLM 生成代码的沙箱**不得**与后端共用 `.venv`。
因此 `pyproject.toml` 里刻意没有 numpy / scipy / matplotlib。

**理由**：同一个环境里跑不可信代码，等于把整个项目和 API Key 都交出去
（`os.environ["DEEPSEEK_API_KEY"]` 一行就能读走）。这不是洁癖，是安全边界。

**推论**：沙箱环境在 M3 单独创建。

### ADR-006：图表与 UI 共用一套色彩体系

**决策**：`web/src/app/globals.css` 是全站视觉的唯一真相来源。组件内禁止硬编码色值。

**理由**：ModelForge 是图表密集型产品。UI 一套色、图表另一套色，成品会像两个产品拼起来的。

**硬性约束（由配色校验计算得出，非审美偏好）**：
- 亮色模式下有 3 个分类色对比度低于 3:1 → 图表必须带**直接标签或表格视图**
- 暗色模式最差相邻 CVD ΔE = 10.3（危险区）→ **必须启用次级编码**（标签/间隙/纹理）

**合起来**：图表永远不能只靠颜色区分系列。

### ADR-007：Agent 自称「蒟蒻」

**决策**：Agent 在文案中自称「蒟蒻」（网络语，新手、菜鸟）。

**理由**：与 ADR-001 自洽 —— 一个承认自己拿不准、每个决策点都停下来问用户的 Agent，
自称越谦逊，交互越不违和。这个调性延续到 Agent 提示词和各处界面文案。

**落地**：`modelforge/agents/prompts.py` 的 `SYSTEM_PROMPT`。前端不传 system 消息时
由后端兜底注入 —— 人设是服务端资产，换人设不该要求用户清浏览器缓存。

### ADR-008：SSE 客户端用 `fetch` + `ReadableStream`，不用 `EventSource`

**决策**：前端手写 SSE 帧解析（`web/src/lib/sse.ts`），不用浏览器内置的 `EventSource`。

**理由**（三条，前两条是硬约束，第三条是它反而帮了我们）：

1. **`EventSource` 只支持 GET，不能带请求体。** 而我们要把整个对话历史发过去，
   天然是 POST 语义。塞进 query string 既有长度上限（几轮对话就爆），
   又会让对话内容完整地留在服务器访问日志里。
2. **`EventSource` 不能发自定义请求头。** M6 要加鉴权时只能退而求其次用 Cookie
   或 query 参数，而后者会把 token 写进日志。
3. **自动重连在这里是有害的。** 普通 SSE（行情、通知）重连是好事，接着收就行；
   但生成流重连意味着**重新跑一遍模型** —— 用户会看到前半句被重吐一遍，
   还白花一份 token。

**修正一处先前的判断**：M2 计划里把「不能自动重连」列成了方案 A 的代价。
权衡时发现这条写反了 —— 对这个场景它恰恰是优点。**待定**状态的解除，
靠的不是收集更多信息，而是发现原先把某一项的符号搞错了。

**已知代价**：约 60 行手写解析（字节碎片 + 帧碎片两级缓冲），且断线不会自愈。
断线恢复交给 M4 的 checkpoint 机制：重连 = 从落盘状态开一条新流，
而不是让传输层偷偷重放。

### 验收结果

- [x] 文字逐字出现 —— 实测 36 帧散布在 862ms 内，帧间隔约 13ms
- [ ] 工具调用状态提示 —— **渲染逻辑已写好，但要等 M3 才有事件可显示**
- [x] 后端挂掉时显示明确错误 —— `response.ok` 与带内 error 两条路径都有覆盖
- [x] ~~断开后重连不产生重复文字~~ —— 按 ADR-008 改为「不做自动重连」，
      恢复能力移交 M4 的 checkpoint

### 三条关键设计

**① 错误分两层，两边都要处理**

    流开始**之前**  → HTTP 状态码（前端读 `response.ok`）
    流开始**之后**  → 带内 error 事件，HTTP 仍是 200

因为响应头必须在第一个字节发出前定死。只处理一层，就会有某条失败路径变成白屏。

**② 碎片是分层的**

M1 处理过「JSON 参数碎片」，M2 又遇到两种更隐蔽的：

    · 字节碎片 —— 中文占 3 字节，分片边界可能把一个汉字劈成两半
                  → `TextDecoder` 用 `{ stream: true }` 模式
    · 帧碎片   —— 一次 read 可能是半帧，也可能是三帧半
                  → 解码成文本后先攒 buffer，再按空行切

共同规律：**不要假设一次到达的就是一个完整单位。**

**③ Finish 一定是最后一个事件**

这条契约跨了三层（Provider → SSE → 前端 for-await 循环），
每层都有责任维护它。`chat.py` 里那道 `except` 保险就是为此存在的 ——
没有它，生成器抛异常会导致前端停在转圈上永远不动。

### M2 顺带修掉的两处旧问题

- `page.tsx` 的 `idle` 状态被删除。它与 `loading` 对用户是同一件事，
  而在 effect 里同步 setState 反而多触发一次渲染。（React Compiler 的
  `set-state-in-effect` 规则抓到的 —— 它抓的是性能症状，暴露的是建模冗余。）
- `performance.now()` 移出组件作用域（`purity` 规则）。时钟读取天然不纯，
  而组件作用域内的一切都被要求可重入。

### ⚠️ 两个只有端到端才测得出来的 bug

这一节是 M3 最值得留下的东西。两个 bug 都有同一个特征：
**86 个单元测试全绿，一接到真实服务器上就炸。**

**① `NotImplementedError:`（消息是空的）**

    起因：Windows 上 asyncio 的 SelectorEventLoop **根本不支持子进程**。
    修法：不用 asyncio 的子进程 API，改用 `asyncio.to_thread` 包阻塞式
          `subprocess.Popen`。任何事件循环都能跑。
    教训：**不要把功能正确性押在「服务器碰巧选了哪个事件循环」上。**
         而且这个选择发生在我们代码被 import 之前，应用层管不着。

**② 随机的 `KeyboardInterrupt`（退出码 3221225786）**

    起因：沙箱每次执行都往**项目目录内**写一个 `solution.py`，
         而 uvicorn 的 `--reload` 正盯着项目目录 ——
         一看有新文件就热重载，重载的终止信号顺着控制台传到了
         正在跑代码的沙箱子进程上。竞态，所以时灵时不灵，
         而第一次 `import numpy` 最慢、窗口最宽，看起来像「第一次必挂」。
    修法：工作目录挪到系统临时目录，并在配置落进项目里时打警告。
    证据：uvicorn 日志里那句
          `WatchFiles detected changes in 'sandbox_tmp\run-xxx\solution.py'. Reloading...`

**共同教训**：单元测试的**环境**往往比真实环境宽松（pytest 用默认事件循环、
不起 reloader）。所以「测试通过」给的是信心，不是证据 ——
每个里程碑都要真的把服务跑起来、用真模型走一遍。

⚠️ **给 M5 的提醒**：生成图表要存「产物」时，**不要**存进项目里的
`artifacts/`，那会重新触发问题 ②。存系统目录 + 接口下载，
或者给 uvicorn 配 `--reload-exclude`。

## 环境备忘

- `.venv` = Python 3.12.4（从 Anaconda base 的 python.exe 创建）
- **系统 PATH 里的 `python` 是 3.7（已 EOL）**，一切操作必须显式用 `.venv/Scripts/python.exe`
- pip 清华镜像配置在 `.venv/pip.ini`（在 venv 内，被 gitignore）
- `.env` 按**当前工作目录**查找，所以命令必须在项目根目录执行
- 从 PowerShell 传中文参数给 Python 是安全的（已验证码点无损）

### 常见故障

| 症状 | 原因 | 处理 |
|---|---|---|
| `WinError 10013` | 端口被占用（报错信息完全没提这点） | `netstat -ano \| findstr :8000` 拿 PID → `taskkill /F /PID <pid>` |
| 前端跑到 3001 端口 | 3000 被占 | **必须在 3000**，因为 CORS 白名单只放行了它 |
| `ModuleNotFoundError: modelforge` | editable 安装的查找器映射为空 | 在项目根目录重跑 `pip install -e .` |
| 沙箱报 `NotImplementedError`（**消息为空**） | Windows 上 SelectorEventLoop 不支持子进程 | 已修：改用线程跑阻塞式 Popen。若复现，检查是否有代码走回了 asyncio 子进程 API |
| 沙箱随机 `KeyboardInterrupt`，退出码 `3221225786` | 沙箱工作目录在项目内，触发了 `--reload` | 已修：默认改到系统临时目录。检查有没有把 `SANDBOX_WORK_DIR` 配回项目里 |
| 沙箱说「解释器不存在」 | 还没建 `.venv-sandbox` | `.venv/Scripts/python scripts/setup_sandbox.py` |
